# v0.6.0 checker constraints

Baseline: [published v0.6.0](https://github.com/pagrus7/kaferry/releases/tag/v0.6.0), commit `d7d485b96a52b711cb10d76dca09aa9b155dec5e`. Authoritative references are the tagged [copy contract](https://github.com/pagrus7/kaferry/blob/v0.6.0/design/decisions.md), [archive contract](https://github.com/pagrus7/kaferry/blob/v0.6.0/design/archive.md), and [client limitations](https://github.com/pagrus7/kaferry/blob/v0.6.0/design/client-compatibility.md). M0/M1 must verify these against the downloaded artifact identity. These notes constrain adversarial assertions; they are not a replacement specification.

- Output is at least once for selected records before completion. Crashes/rebalances may duplicate and reorder. Saved progress may advance only through the consumed prefix whose records have been acknowledged, filtered, or synchronously skipped; Kafka gaps do not represent missing records.
- PRESERVE is default: original partition N maps to destination N, including null keys. KEY uses Java Murmur2 for non-null keys; null keys use sticky routing. Validate null-key bytes and valid destination membership, not a fixed partition. Archive provenance, not its virtual replay cursor, controls preserved routing.
- Selected source IDs must exist in the destination under PRESERVE. Assignment rechecks layout. Layout checks and publishing are not atomic: midrun change can fail after partial output. Missing partitions must not silently reroute or become SKIP.
- IN selects fixed IDs; NOT IN may discover eligible additions while workers run. Excluded Kafka partitions are not assigned/fetched/committed. External assignment and offset observations do not establish absence of fetch requests without protocol evidence.
- Named groups are required for planned recovery. Omitted GROUP creates a fresh ONE_OFF group each time. Saved positions override START. No group-wide completion barrier exists; worker exit zero, idle exit, or `status: stopped` does not prove complete input delivery.
- During revocation, workers save confirmed progress and release without draining pending deliveries. Late old-assignment results are discarded. Lost ownership cannot save progress. Initial/periodic commit errors fail; specified transient revocation commit errors release for replay. Do not infer generation IDs from group descriptions.
- Async delivery errors fail under every policy. SKIP can handle applicable synchronous record rejections, not arbitrary rejected batches. Delivery deadlines and shutdown bounds come from effective configuration and the tagged contract. Consumer transient polling retries have no general total deadline; tip wait bounds only the sampled-tail wait.
- Timestamp cutoff is heuristic. A high timestamp can stop a partition before a later-offset in-window record, even when already present. Catch-up samples a fixed log end including open transactions; committed reads must reach that end or time out. Use controlled timestamp/transaction fixtures with independently justified obligations.
- Ordering is only promised from one source partition to one destination partition in an uninterrupted producer session with stable routing. Work caps bound tracked unsaved work, not total RSS or the maximum duplicate count after arbitrary restarts.
- Archive capture syncs data and recovery state before confirming records for source progress. Recovery may truncate unacknowledged tails; completed files are immutable. Inspect recovered data as well as completed files before declaring loss.
- Archive replay pins completed selected files before output. Same-group resume does not discover new files and validates its saved selection. Original partition predicates apply across all represented topics/clusters. Fresh selection validates every completed header but only selected payloads; excluded files are not resume obligations. Physical duplicate records remain separate replay obligations.
- Source timestamps outside ±9,223,372,036,854 Unix milliseconds have a documented franz-go decoding limitation. Characterization must identify that limitation rather than silently weakening an ordinary fidelity check. File-to-Kafka timestamp handling is separate and depends on destination rules, including LogAppendTime restamping. Do not turn extreme timestamps into a mandatory broad codec matrix here.

The lab must record the actual fault, applicable contract, and supported inference for every assertion. Unknown contract behavior calls for tagged-source investigation and a documented limit, not a convenient expectation copied from observed Kaferry output.
