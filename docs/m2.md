# Targeted M2 release runs

These development runs exercise the pinned published v0.6.0 executable. They are part of the unfinished M2 milestone; neither a scenario `PASS` nor green harness CI qualifies Kaferry. M0–M6 acceptance requires every mandatory interaction and its independent evidence.

Use a clean committed lab build on native Linux AMD64, Go matching `go.mod`, Docker, network access and GitHub CLI with the provenance-verification support described in [setup](setup.md). Workloads contain only generated synthetic records. The fixture creates two disposable brokers with unique run labels and loopback ports. Never supply an unrelated broker or container.

```sh
set -eu
mkdir -p .cache/bin
go build -o .cache/bin/lab ./cmd/lab
run_id="m2-$(date -u +%Y%m%d%H%M%S)-$$"
cleanup() { go run ./cmd/fixture down "$run_id"; }
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
go run ./cmd/fixture up "$run_id"
.cache/bin/lab scenario "$run_id" healthy PRESERVE "artifacts/$run_id"
.cache/bin/lab check "artifacts/$run_id/bundle"
```

Choose a fresh run ID and output directory for each attempt. `scenario` accepts `RUN_ID CASE ROUTING NEW_OUT_DIR`; it loads this run's fixture manifest, reserves the new directory, and verifies the release archive, provenance and native version afresh. It admits no caller-supplied executable or persisted verification claim. Before launch, read-only probes must confirm that this named group's coordinator is available; a broker API response alone is insufficient. The workload has 96 finite, independently read-back records across three source partitions, including byte-fidelity fixtures. `PRESERVE` retains source partitions; `KEY` uses independently checked key routing to five destination partitions.

The compiled case names are `healthy`, `repeated-kill`, `delivery-stop`, `delivery-threshold`, `source-startup` and `source-save`. Their required observations are defined in [M2](../ROADMAP.md#m2--integrated-crashes-long-stalls-and-timeouts). An accepted name does not establish a reached fault: missing independent fault or timing evidence cannot pass. Native CI exercises the healthy PRESERVE/KEY controls, source-startup and repeated-kill cases; the remaining mandatory variants still need implementation and measured evidence.

Packet capture is unavailable. CI retains a separate `UNSUPPORTED` packet status and the denied run reference without attempting capture. A passing data history supplies no packet or timeout-path evidence.

A run retains release-verification files under `release/`, operation observations, worker configuration, queries and logs under `runtime/`, and the finalized four-file offline history under `bundle/` when it can be written. The command prints its report and checker result as JSON. Use the [single exit-code table](setup.md#check-a-bundle-offline) to interpret the status. A command error may retain partial evidence without a checkable bundle; preserve it and use a new directory after fixing the cause.

Send SIGTERM or interrupt the lab command to cancel a run. The controller restores its owned services and reaps its children with a fresh cleanup budget, then retains available observations. The command has a ten-minute context; scenario work has five minutes, followed by up to 150 seconds for restoration and final observations. An expired work budget cannot pass. Fixture creation and final fixture removal are separate commands with their own bounds.

Before ending a successful copy or recovery phase with SIGTERM, the controller
observes complete output, a stable assignment and saved next positions through
every finite source end while that worker is still live. During rebalance an empty assignment means
unknown ownership, so polling continues within the experiment budget. Existing
output alone cannot establish recovered progress. The final settled audit also
requires every source end to be saved. Missing completion prevents PASS and does
not downgrade an independently proved data violation. This completion requirement
asserts no product availability deadline and attributes no save to a particular
member.

The controller restarts the same named Kaferry group during recovery cases. A new CLI invocation starts a new case with new topics and a new group; it does not resume a partially written evidence directory. If cleanup was interrupted, rerun `go run ./cmd/fixture down "$run_id"` using its retained fixture manifest. Cleanup checks resource names and labels and keeps the evidence files.

At safety audits the controller stops and reaps workers, restores services, restarts the owned brokers to settle pending requests, verifies retained source input, and scans every destination partition to recorded ends. The checker compares bytes, membership, routing and saved source prefixes. Container restart preserves broker storage; it is not power-loss testing. A later successful copy cannot repair an earlier unsafe saved prefix. Offline rechecking needs no Kafka, network or Kaferry executable.

Each worker's wait receipt records Linux peak RSS and user/system CPU with explicit units. RSS describes the owned child's wait accounting; CPU may include waited descendants. RSS does not measure tracked-record limits or total process-tree memory. The checker derives SIGTERM-to-wait ranges, including observed deadline overshoot, and final output/input volume from the retained events. Wait includes log draining and controller scheduling; its overshoot does not establish the kernel exit time. Aggregate volume can hide loss compensated by replay, so membership and saved-prefix checks remain separate.

The optional `fixture up-links` source adds a digest-pinned stock Toxiproxy
fixture with worker endpoints separate from direct observer endpoints. Its
ownership, private failure-retention, direct Kafka readiness and topology
controls are implemented as source. Native compilation/unit checks and
accepted proxy-runtime evidence are separate requirements; current status is
recorded in PROGRESS.md.
The opt-in `TestLiveOwnedWorkerLinkTopology` and
`TestLiveOwnedLinkDirectionalLatency` controls do not run in the current CI
matrix. They are calibration, not released-Kaferry qualification. The nonce
latency control targets short directional delays on persistent and new
connections; long delays and pending-response removal remain unmeasured.

The linked Docker/direct-readiness boundaries retain bounded raw failure
notices under owner-only
`.cache/fixtures-private/`, separately from safe selected facts under
`.cache/fixtures/`. Raw notices are excluded from public artifact uploads.
A durable private retention route must be reviewed before proxy execution on
an ephemeral CI runner; runner-local files and public hashes alone do not
retain exact notices after teardown. Encryption alone does not satisfy the
reviewed/redacted publication rule. No proxy runtime is enabled by this source
integration.

Source review found additional in-process HTTP/TCP notice-retention,
public-error suppression and mixed-error retry gaps in the opt-in controls.
Their source repairs and literal failure controls are integrated for affected
review and native checking. No general safe-runtime or durable-notice claim
follows from those unexecuted repairs.

The [private-notice helpers and current publication gate](private-notices.md)
are source integrations with local synthetic controls. Their separate unit
checks do not enable proxy runtime or public encrypted retention.

A separate static function-PC map uses only public ELF/Go metadata from the
pinned executable. The native probe reads the already verified file as data;
it starts no debugger and observes no instruction or fault. Missing/ambiguous
points remain unsupported. This prepares an observation candidate and cannot
remove any timeout, threshold-drain, source-save or worker-ACK evidence gate.
