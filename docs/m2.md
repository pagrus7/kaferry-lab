# M2 release runs and acceptance

M2 is unfinished. Test only the pinned published Kaferry v0.6.0 executable against
the [tagged contract](contract-v0.6.md), using independent record/progress
observations. A successful harness check, calibration or individual history
does not qualify Kaferry. `lab qualify` currently returns `UNSUPPORTED` with
`release_qualified:false`. The [roadmap](../ROADMAP.md#m2--integrated-crashes-long-stalls-and-timeouts)
and [evidence rules](evidence.md) remain mandatory.

## Execution and custody

The selected qualification target is native Linux ARM64 in the owned OrbStack
machine `kaferry-lab-arm64-20261026`, orchestrated from the Mac. Published Linux
binaries and live campaigns run there; Mac builds, unit controls and offline
checking do not establish native fault behavior. Preserve historical AMD64
bundles and their offline-checking support without attributing ARM64 execution
to them. See [native platform boundaries](local-linux-arm64.md).

Use a clean reviewed lab checkout and the ordinary Go toolchain/caches. Record
the actual source, Go/kernel architecture pair, Docker backend, artifact bytes
and resource ownership. Every release invocation must derive from freshly
verified published artifacts; no caller-supplied executable, cached verification
claim, Kaferry source build, application import or internal-codec oracle is allowed.
The sibling Kaferry checkout stays read-only.

Raw evidence stays private locally. Passing run custody requires actual
writer/process closure, bounded guest capture and independent Mac readback;
preserve failed prefixes as incomplete. The active
[workflow](../.github/workflows/ci.yml) runs only fixed no-child Python custody
calibration on the owned Mac runner. At source `6121153`,
[run 40847737833](https://github.com/pagrus7/kaferry-lab/actions/runs/40847737833)
passed eight steps with zero artifacts; the separate manual native harness
check passed in 54.679 seconds. Neither is a native product campaign or general
proof of writer closure. Full native CI/campaign custody integration remains incomplete.
There is no active encryption, artifact/cache upload or Tailscale route.
See [local runner custody](local-runners.md) and the
[hardware caller boundary](hardware-custody.md).

Read [PROGRESS.md](../PROGRESS.md) before selecting a run: it owns current commits,
resources, stopped operations, evidence locations and exact next actions.
Packet capture and global process enumeration remain stopped. Retain new
refusals and stop their selected operations; do not change user, cache, verifier,
debugger, privilege or safeguards to obtain another route.

## Implemented command interfaces

Build the lab, keeping Go VCS information for scenario admission:

```sh
./scripts/check.sh
mkdir -p .cache/bin
go build -buildvcs=true -o .cache/bin/lab ./cmd/lab
```

The check script runs caller controls and formatting/vet/race/unit checks.
Skipped live tests are not capability evidence. The following are implemented
interfaces; uppercase arguments mean explicit fresh paths or owned run values,
not a preconfigured campaign:

| Command | Meaning and prerequisite |
| --- | --- |
| `.cache/bin/lab verify NEW_OUT_DIR` | Fresh release/tag/checksum/provenance/native-version verification on a matching native Linux platform. |
| `.cache/bin/lab scenario RUN_ID CASE PRESERVE NEW_OUT_DIR` | Targeted release attempt using that run's retained fixture manifest and a new evidence directory; `KEY` is also accepted. |
| `.cache/bin/lab check BUNDLE_DIR` | Deterministic offline checking; no Kafka, Docker, network call or target executable is needed. |
| `.cache/bin/lab calibrate NEW_OUT_DIR` | Separate healthy/faulty stand-in controller calibration, not a Kaferry run. |
| `go run ./cmd/fixture up RUN_ID` | Create the uniquely owned two-broker fixture, subject to backend/image admission. |
| `go run ./cmd/fixture up-links RUN_ID` | Create the optional stock-proxy fixture with its private evidence/image authority. |
| `go run ./cmd/fixture env RUN_ID` | Print this fixture's selected environment values. |
| `go run ./cmd/fixture down RUN_ID` | Remove only admitted resources from its retained manifest, when the selected facility permits cleanup. |

These interfaces are not an accepted end-to-end recipe for every backend. The
selected containerd-store image proofs currently require linked-fixture private
authority; the nonlinked setup path refuses the modern proof before resource
creation. Do not bypass that refusal or invent a different fixture identity.
[Native image admission](local-linux-arm64.md#containerd-store-admission-and-development-observations)
describes the boundary.

The implemented `cmd/link-calibration` owns linked setup, one fresh native test
child and permitted cleanup. Its required flags are `--repository`, `--run-id`,
`--test-binary`, `--test-sha256`, `--reviewed-head` and `--built-after` (UTC
RFC3339Nano). Values must bind the exact clean native driver/test build, fixed
build paths, fresh attempt and private custody route; the command builds and
publishes nothing. A manual `up-links` call does not supply its parent waits or
writer-closure evidence. Use the reviewed native caller/retention path rather
than treating standalone test output as custody proof.

## Scenario support and missing observations

The CLI uses 96 finite records across three source partitions, including byte
fixtures; it independently reads back the input before faults. It records a
named group for same-group recovery. Start with `PRESERVE`; repeat only faults
sensitive to routing with `KEY` and independently checked destination routing.

| Compiled case | Implemented development behavior and acceptance limit |
| --- | --- |
| `healthy` | Complete copying, saved progress and settled audits; a comparison control, not a fault. |
| `repeated-kill` | Seeks two output-lag kills and a separate visible-output/unsaved-position crash, then same-group recovery. Every window and actual signal exit must be observed. |
| `source-startup` | Source impairment before invocation, bounded exit, restoration and recovery. A scheduled hold does not identify a particular coordinator RPC. |
| `delivery-stop` | Destination outage/hold plus SIGTERM and recovery are staged, but independent delivery-timeout-path/accepted-work overlap is still missing. |
| `delivery-threshold` | Accepted name, explicitly unsupported before workload preparation: accepted-record threshold and drain-entry witnesses are missing. |
| `source-save` | Stages source outage and recovery but cannot establish a periodic save was hit; it retains the unsupported observation and fails that mechanism. |

The two-phase checker/profile work is preparation, not another runnable scenario
command. Required delivery controls need a warmup of 3 records and full input of
96 records, the correct primary profile (threshold of 4 or unlimited), and a
separate unlimited recovery. Live SIGTERM past delivery timeout and failed
threshold drain are distinct requirements. Periodic source-save needs progress
from the same worker after the warmup of 3 records, a newly visible unsaved
record, full membership of 96 records, a current checkpoint-save origin and an
actual impaired-save failure. Startup, final-save and revocation observations
cannot substitute.

Native `links-native-20261028e` has independently accepted bounded generic TCP
calibration: 19 exact nonce exchanges covered 400 ms directional and 20 s
downstream delay, existing/new sockets, toxicity zero, removal and recovery, with retained
mappings/logs/waits/cleanup. Its pending byte arrived after recorded HTTP DELETE
return, inside the larger callback/evidence-retention envelope. This establishes
no Kafka response type, worker ACK, timeout, drain or save path. See
[coverage and timing limits](coverage.md#m3--ownership-links-transactions-and-discovery).

Hardware normal and normal-c attempts remain failed before inferior execution;
normal-c reached startup/guard readbacks then rejected a fixed catchpoint
notification. No hardware hit or current release frame was observed. Source,
build and literal controls do not supply current caller/accepted-error/token/
context/stack ownership or released-worker original-parent launch/wait receipts.
[Hardware custody](hardware-custody.md) and PROGRESS track repair status and
prerequisites for a fresh run.

## Evidence required for every accepted case

- **Given:** verified published subject and tagged contract, independently verified
  finite ledger of 96 records across three partitions, known fixture/topic/group identities,
  healthy comparison, explicit budgets/configuration and private evidence sinks.
- **When:** for a fault case, bind the trigger to current independently observed
  work; retain the requested fault, proof it reached that work, actual process
  waits and fault interval. Timers, logs, output lag, broker processing or a
  historical same-LWP hit cannot manufacture a current accepted-work/drain/save/
  ACK witness.
- **Then:** restore the owned services, reap workers, settle pending-output
  ambiguity and recover the same group. Reverify the source ledger after
  restoration and required settling broker restarts. Fully scan every destination partition
  to recorded ends, verify full required membership/bytes/routing and audit safe
  saved prefixes. Recovery duplicates are permitted; later output cannot repair
  an earlier unsafe saved prefix. Final saved positions must reach every finite
  source end. Missing observations, incomplete cleanup/scans and product
  violations cannot become PASS.

The scenario command has a ten-minute context; work is five minutes with a fresh
150-second cleanup/audit budget. Fixture creation/removal are separate bounded
operations. Cancellation attempts owned restoration/reaping and retains failures;
an expired budget or failed sink stays incomplete. Only exact run-owned resources
may be touched. Do not automatically retry `down` or switch cleanup routes after
a retained facility stop; preserve unresolved resources and the original notice.

Runs retain `release/`, `runtime/` and, when finalization succeeds, the four-file
`bundle/` (`manifest.json`, `artifact.json`, `events.jsonl`, `complete.json`). Use
new run IDs and output directories; a new invocation creates new topics/group,
not continuation of a partial directory. Keep originals under `.cache/` or
`artifacts/`, never force-add or upload raw evidence. RSS/CPU/wait intervals have
recorded units and scope; they do not prove tracked-work limits, exact kernel
exit time or power-loss durability.

After target absence, perform two identical checks of the unchanged bundle in a
recorded network-isolated environment using `.cache/bin/lab check BUNDLE_DIR`.
Keep both results and source identity. There is no extra `--offline` flag;
offline isolation is an execution/evidence requirement. Use the
[checker exit-code table](setup.md#check-a-bundle-offline) and
[schema contracts](../internal/evidence/README.md) to interpret the JSON result.
Full M2 acceptance requires all roadmap cases, calibrated observers, complete
independent audits, frozen reviews and final-head CI; M3–M6 remain required too.

Historical hosted matrices/encrypted transport are retained in git and
[legacy private-notice history](private-notices.md). That document is a historical
reference here, not an instruction to reactivate transport. Detailed failed runs,
recovery limits and private bundle paths belong in PROGRESS and retained evidence,
not a second execution diary in this guide.
